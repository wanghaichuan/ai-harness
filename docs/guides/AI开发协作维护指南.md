# AI 开发协作维护指南（模板）

> 人机协作的完整工作手册：**标准定位 → 开发流程 → 修改 → 验证 → 工作流闭环**。
> 复制本模板后按项目实际路径、业务域补全。

---

## 一、标准定位（改代码前先找依据）

| 顺序 | 查什么 | 回答什么 |
|------|--------|----------|
| 1 | 业务词索引 `docs/guides/业务词到代码入口索引.md` | 业务词对应哪个 Controller/Service |
| 2 | 产品规则 `docs/product/` | 需求是否越界 |
| 3 | 隐性约定 `docs/architecture/implicit-contracts.md` | 历史坑点、口头约定 |
| 4 | 规范 `docs/standards/` | SQL/测试硬性标准 |
| 5 | 版本文档 `docs/versions/<版本>/` | PRD、接口清单、库表设计 |
| 6 | 变更工件 `openspec/changes/`（或 `archive/`） | 提案/设计/任务范围 |

**不要猜测。** 依次：查文档 → 查代码 → 查 `docs/records/` → 问人。

---

## 二、开发流程（版本需求的标准开发链路）

```
① 读需求+原型 → ② 整理接口 → ③ 库设计+脚本 → ④ 跑脚本 → ⑤ 编码
→ ⑥ 写接口实现说明与测试用例 → ⑦ 接口测试 → ⑧ 测试报告
→ ⑨ 整合变更工件到 openspec/changes → ⑩ 确认无误后归档 archive
→ ⑪ 更新业务词索引 + CodeGraph + 记忆
```

| 步骤 | 做什么 | 产出（落位） |
|------|--------|-------------|
| ① 读需求文档和原型 | 读 PRD + 原型，理解业务规则、边界 | 需求理解与疑问点（歧义先问清） |
| ② 整理需要开发的接口 | 标注新增/改造/复用，定路由、入参出参 | **接口清单**（`开发/`） |
| ③ 编写数据库设计文档和脚本 | 表结构、字段映射；写增量 SQL | **库设计文档 + SQL 脚本**（`开发/`） |
| ④ 运行脚本 | 在开发库执行验证（**脚本由人手动执行，禁止 AI 自行执行**） | 库表就绪 |
| ⑤ 编写代码 | 按分层实现；计算/校验逻辑分离 | 代码 + 迁移 SQL（增量） |
| ⑥ 编写接口实现说明与测试用例 | 实现要点、约定、逐接口用例 | **实现说明与测试用例**（`开发/`） |
| ⑦ 进行接口测试 | 逐用例实测，问题回 ⑤ 修复回归 | 测试记录（`测试/`） |
| ⑧ 输出测试报告 | 通过率、缺陷与修复、遗留项 | **测试报告**（`测试/`） |
| ⑨ 整合变更工件 | 设计决策收敛为 提案/设计/任务（中文 change 名） | `openspec/changes/<中文change名>/` |
| ⑩ 确认无误后归档 | 对齐校验 + 评审全过 → 移入 archive | `openspec/changes/archive/` |
| ⑪ 更新索引与记忆 | 新增/变更的业务词补进业务词到代码入口索引；`codegraph sync`；更新项目记忆 | 业务词索引 + 索引新鲜 + 记忆刷新 |

### 注意事项

1. **数据库脚本需要自己手动执行，禁止 AI 自行执行**——AI 只负责编写和检查脚本，执行权在人
2. 原型设计放 `versions/<版本>/design/`，**文件过大过多不上传仓库**，提交时注意
3. 版本文档按 **需求 / 开发 / 测试** 三类归位
4. SQL 注意目标库方言（如 PG 与 MySQL 函数差异）
5. 小型改造可直接走四步（propose → apply → verify → archive），不必套版本十步

---

## 三、修改（怎么改才算合规）

- **没有变更依据不写代码**（版本文档 / change 工件）
- **编码前更新 codegraph 和记忆**
- 四原则：编码前思考 / 简洁优先 / 精准修改 / 目标驱动执行
- 硬性红线（按项目补全）：禁改环境配置、禁改已有迁移 SQL、禁 AI 执行数据库脚本、禁危险命令、不跨层调用、SQL 禁 `${}` 拼接

---

## 四、验证（改完怎么证明是对的）

| 层级 | 手段 | 通过标准 |
|------|------|----------|
| 编译 | 构建通过 | 0 error |
| 单元测试 | JUnit + Mockito | 新 Service 核心方法有单测 |
| 接口测试 | 全链路，真实数据库 | 按测试用例逐条通过 |
| 流程对齐 | verify | 实现与文档一致 |
| 专项评审 | 评审四连 | 无 BLOCKER/FAIL |

评审不通过标准：SQL 注入、无规格核心逻辑、跨层调用、改已有迁移 SQL、认证被绕过。

---

## 五、Workflow 流程（端到端闭环）

```
propose  →  apply  →  verify  →  archive
```

工件结构：`openspec/changes/<中文change名>/` 提案.md + 设计.md + 任务.md +（评审产物）

---

## 六、编码前强制动作：更新 CodeGraph 与记忆

```bash
codegraph status   # 看索引新鲜度
codegraph sync     # 不新鲜则同步
```

检查并更新项目记忆（`MEMORY.md` 体系），修正过期内容。
